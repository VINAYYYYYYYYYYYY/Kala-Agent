# native-design REPORT: kala-studio serves design and geometry natively

Cell: `cutover-20261020/native-design` (Rust worker)
Scope: `backend/crates/kala-studio/**`, plus one mechanical line in
`backend/Cargo.toml` and the regenerated `backend/Cargo.lock` (see
§2). No commit, push, delegation, sudo or credential reads.

Status: **complete**. The front door's geometry backend is now the native
one: the real OpenCascade adapter (`kala-cad`), the reviewed CAD provider
connections (`kala-cad-providers`), the reviewed design-intent contract
(`kala-design-intent`) and the reviewed session journal
(`kala-studio-journal`). A default launch starts **no Python process**, and
all four live differentials report **0 mismatches** against the live Python
public server.

**The user's real data was never touched.** Every shell ran with `HOME`,
`KALA_AGENT_DATA_DIR`, `KALA_STUDIO_DATA_DIR` and `XDG_DATA_HOME` pointed at
fresh `mktemp -d` directories, and every test writes only into a
`tempfile::TempDir`. The path `~/.local/share/kala-agent/**` was never read,
written or named in a command.

---

## 1. What changed in the product

| Before (ADR-0010 phase 1) | Now (ADR-0010 phase 2) |
|---|---|
| the front door supervised **one Python geometry worker** and proxied the geometry, design, journal, intent and import routes to it | the front door serves those routes **itself**, from the native crates |
| the worker was started by default | the worker is started **only** when `KALA_STUDIO_GEOMETRY_WORKER` names one (the development fallback) |
| `default = []` (no native geometry at all) | `default = ["native-geometry"]` (the native geometry backend) |

`POST preview`, `POST export`, `POST handoff`, `POST design`,
`GET design/{id}/drawing`, `GET design/{id}/section`, `GET journal`,
`GET journal/verify`, `GET providers/cad` and `POST import` are now answered
natively. `GET health`, `GET integrations`, `GET providers`, `GET/POST
settings` and `POST chat` were already native and are unchanged.

The worker path is untouched: `tests/worker_differential.py --backend worker`
runs the same 292-case matrix against the supervised Python worker and
reports 0 mismatches as well.

### Outside the owned path (one mechanical change, declared)

`backend/Cargo.toml`: the crates the native backend depends on are separate
standalone workspaces, and Cargo refuses a path dependency on a second
workspace root unless the root manifest excludes it. The `exclude` list
already carried `kala-contracts` and `kala-process` for exactly this reason
(the `workspace` cell did it); the five new path-dependency crates
(`kala-cad`, `kala-cad-providers`, `kala-solidedge-client`,
`kala-design-intent`, `kala-studio-journal`) were added to the same list.
`backend/Cargo.lock` was regenerated by cargo as a consequence.

**No other crate's source, manifest, public API or test was touched**, and no
Python source, shared fixture, adapter or `studio/**` file was touched. The
`exclude` list is a registration, not a behaviour change: without it the
workspace does not resolve at all.

### The declared native-identity differences

Two facts are true of the native build and are declared in the harnesses
instead of being hidden. Every other byte is compared.

1. **The OpenCascade provider version.** The Python side reports the version
   of the `cadquery-ocp` binding it imports (`8.0.1.1`); the native side
   reports the version of the OpenCascade SDK it links (`7.9.3` on this
   host). They are two identities of the same kernel family and they are not
   comparable. The harnesses replace the field with a placeholder **only**
   for the `opencascade` provider; the FreeCAD and Solid Edge identities are
   still compared exactly.
2. **The display mesh vertex order.** The two OpenCascade versions assemble
   the same STEP file with the faces in a different order, so the imported
   triangulation is the same geometry in a different order. The harnesses
   compare the mesh by an **order-independent fingerprint**: the sorted
   `(position, normal)` vertices and the sorted triangles, each written as
   its three corners, plus the exact vertex count, triangle count, bounds,
   solids and warnings. The two fingerprints are equal: the vertex set, the
   triangle set, the counts and the bounds are identical, and only the array
   order differs. (Verified directly: importing the *same* STEP file with
   the native reader and with the Python reader gives the same 586 vertices
   and 568 triangles and the same sorted triangle set.)

The generated artifact digests (`step_sha256`, `native_sha256`) are volatile
by construction: the OpenCascade STEP writer and the FreeCAD FCStd writer
embed the wall clock of the write. The harnesses mask them and check that
they are still 64-character lowercase hexadecimal digests.

The `content-length` header follows the body, so it is compared exactly for
the answers whose body is byte-identical and is compared through the
normalised document for the ones with a declared native identity.

### The Windows cross-check

The target `x86_64-pc-windows-gnu` **is** installed, but the check cannot
complete on this host:

* it fails inside `ring` (the TLS crate every build pulls in) with
  `failed to find tool "x86_64-w64-mingw32-gcc"` — the MinGW cross
  compiler is not installed yet. The wave's own rule is that the user
  installs `mingw-w64-gcc` and the `windows-check` cell runs afterwards.
  The same failure occurs with `--no-default-features`, so it is not caused
  by the native geometry.
* the **OCCT-linked** build additionally needs a Windows OCCT SDK
  (`OCCT_INCLUDE_DIR` / `OCCT_ROOT` / `VCPKG_ROOT`), exactly as the
  `cad-r2` and `cad-r3` reports state. The native geometry is behind the
  `native-geometry` feature, so `cargo check -p kala-studio
  --no-default-features --target x86_64-pc-windows-gnu` is the portable
  surface the wave's Windows script can use.

**No Windows build, no Windows runtime and no packaging cutover is claimed.**

## 8. Compatibility evidence

* **Byte-exact responses.** The design document, the view-only import
  document, the journal page, the journal verification, the journal event,
  the CAD provider list, the intent parse and validate documents, the
  drawing and the section are built in Pydantic field order and serialised
  with pydantic-core's float text (the Rust `serde_json`/`ryu` form). The
  refusals keep the two orderings the Python source uses: the Pydantic
  model order (`code`, `message`, `details`) for framework validation, and
  the sorted `json.dumps(..., sort_keys=True)` form for route refusals.
* **The corpus.** The frozen 56-case corpus replays byte-for-byte, including
  the design document, the HLR drawing and the exact-area section.
* **The journal.** The native journal is the reviewed `kala-studio-journal`
  crate, byte-compatible with the Python journal. The cold reload is proven
  in `tests/native_geometry.rs`: the **Python** implementation writes the
  journal and the artifacts, and the native service then loads the design
  back from that journal (`cached: true`) with the same design id, the same
  measured numbers, the same checks, the same script digest, the same STEP
  digest and the same view.
* **The provider rule.** The view is always the OpenCascade import of the
  provider's own STEP bytes, and OpenCascade is never the measuring
  authority for an external model: the FreeCAD provider's own numbers are
  the ones the design reports, and the differential's real FreeCAD chat
  build (`design.chat_with_freecad`) is compared against the live Python
  server.
* **The refusals.** The provider-required refusal, the unknown-provider
  refusal, the unusable view selection, the unusable plane and offset, the
  unusable journal page, the unknown design and the STEP import refusals
  were compared with the live Python server and match byte-for-byte.

## 10. Intentional differences and remaining gaps

1. **The OpenCascade binding differs** (system OCCT 7.9.3 here, the
   Python oracle's `cadquery-ocp` 8.0.1.1). The declared consequences are
   the provider version and the display mesh vertex order (§5). The
   geometry, the measurements, the checks, the drawing and the section are
   identical.
2. **The native cache holds the plain view data, not the kernel handle.**
   `kala-cad`'s `Shape` is deliberately `!Send + !Sync`, so the design cache
   cannot own it. A drawing or a section therefore re-imports the stored
   STEP artifact instead of reusing a cached shape. The answer is
   identical; the work is not. The Python service keeps the shape in its
   cache.
3. **The drawing and the section re-import the provider's STEP.** That is
   the same "the view is the provider's export" rule, applied to the
   drawing: the HLR views and the section loops are computed on the
   imported provider shape, never on a locally recompiled shape.
4. **The design request's field-level validation kind is approximated.**
   The provider refusals (missing, unknown) are exact. A field-level
   intent error reports the reviewed `kala-design-intent` message with the
   `value_error` kind, where Pydantic would name a more specific kind
   (`greater_than`, `string_type`, …). The message text and the location
   are the same. The corpus and the differentials do not exercise that
   path.
5. **The OpenCascade STEP export is not byte-stable between two exports.**
   The writer embeds the wall clock and its own entity numbering. The
   geometry, the units, the solid count, the volume and the bounds are the
   contract; the raw bytes are not. This is the accepted `kala-cad`
   behaviour, not a new difference.
6. **The native build has no `step_available: false` mode at runtime.** The
   `native-geometry` feature links the kernel; a build without the feature
   (`--no-default-features`) is the explicit portable mode, and the
   capability probe reports `design_available: false` when the kernel
   cannot execute.
7. **The worker's development default is gone.** `WorkerCommand::
   from_environment` still knows a development default, but the front door
   no longer starts a worker unless `KALA_STUDIO_GEOMETRY_WORKER` names
   one. A developer who wants the old behaviour sets the variable.
8. **The `corpus_fixture` test's STEP-exporter check follows the feature
   that actually links the exporter** (`native-primitives`, not its
   `native-step` alias). The test was previously compiled out of the
   default build, so the check never ran; it now runs and passes.
9. **One flake was observed** in `tests/chat_with_design.rs` during a
   release run under heavy load (the whole suite was rebuilding at the
   time). It did not reproduce in four subsequent runs of that suite, in
   three full release runs, or in the debug run. The failing assertion was
   on the chat reply text of a design prompt, which depends on the worker's
   `intent/parse`; the worker was not the subject of any change.
